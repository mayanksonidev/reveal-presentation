Kubernetes Probes

Ensuring Application Health and Reliability

Why Do We Need Probes?

Without Probes ❌

K8s only knows if your container process is running.

It doesn't know if your app is deadlocked, crashing, or stuck loading data.

With Probes ✅

K8s understands the actual state of your application.

It can automatically restart failed apps and route traffic only when ready.

The Probe Sequence

Probes happen in a very specific order during a Pod's lifecycle.

1. Startup

Has the application finished initializing?

➔

2. Liveness

Is the application still alive and healthy?

➔

3. Readiness

Can it accept network traffic right now?

🚀

1. Startup Probe

  • Purpose: Protects slow-starting applications.
  • Behavior: While the Startup Probe is running, all other probes are disabled.
  • Outcome: If it fails (times out), K8s kills the container and restarts it. Once it succeeds, it never runs again for the life of the container.

Startup Probe Configuration


apiVersion: v1
kind: Pod
metadata:
  name: slow-legacy-app
spec:
  containers:
  - name: my-app
    image: my-company/slow-app:v1
    startupProbe:
      httpGet:
        path: /health/startup
        port: 8080
      failureThreshold: 30
      periodSeconds: 10

This app gets up to 5 minutes (30 * 10s) to start before K8s gives up.

💓

2. Liveness Probe

  • Purpose: Determines if a container needs to be restarted.
  • Behavior: Runs continuously after the Startup probe succeeds.
  • Outcome: Catches deadlocks. If the app is stuck and cannot recover itself, the liveness probe fails, and K8s brings up a fresh instance.

Liveness Probe Configuration


    # Inside the container spec...
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 3
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 3

initialDelaySeconds: Wait before first check.

failureThreshold: How many strikes before restarting.

🚦

3. Readiness Probe

  • Purpose: Determines if the app is ready to receive user traffic.
  • Behavior: Runs continuously. Checks if downstream databases or caches are available.
  • Outcome: If it fails, K8s removes the Pod's IP from the Service endpoints. It does NOT restart the Pod! The app is just temporarily hidden from users.

Readiness Probe Configuration


    # Inside the container spec...
    readinessProbe:
      exec:
        command:
        - cat
        - /tmp/ready
      initialDelaySeconds: 5
      periodSeconds: 5
      successThreshold: 1

We can use exec, tcpSocket, or httpGet for any probe type!

Recap & Summary

  • Startup: Gives slow apps time to boot. Prevents premature kills.
  • Liveness: Monitors for catastrophic failures. Restarts the container.
  • Readiness: Monitors for temporary issues. Pauses incoming traffic.

You need BOTH Liveness and Readiness for robust K8s applications.
