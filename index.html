What is a Multi-Service Deployment?

  • Breaking down applications into smaller, independent components.
  • Running different parts (e.g., API & Database) in their own isolated Pods.
  • Each service can scale and update independently without affecting others.

Why? Better security boundaries, fault isolation, and decoupled architecture.

❓

The Communication Problem

  • Pods are ephemeral — they are destroyed and recreated constantly.
  • Every time a Pod starts, it gets a new internal IP address.
  • You cannot hardcode Pod IPs in your application!

How do pods reliably find each other if IPs keep changing?

🛡️

Services to the Rescue

  • A Service is an abstraction that provides a stable, unchanging IP Address and DNS name.
  • It acts as a load balancer, automatically tracking changing Pod IPs in the background.
  • ClusterIP: The default service type. It creates an internal IP reachable only from inside the cluster. Perfect for databases!
🔌

How Connection is Established

1. App Config

App uses the target Service name (e.g., mysql-svc).

➔

2. CoreDNS

K8s built-in DNS resolves mysql-svc to the stable Service IP.

➔

3. Routing

Service routes request to a healthy backend Pod.

💡

Crucial Takeaways

  • Environment Variables: Pass Service names into your Pods via environment variables (e.g., DB_HOST=mysql-service). Don't hardcode them.
  • Isolation: Never expose databases to the outside world. Keep them securely on a ClusterIP Service.
  • Automatic Load Balancing: If you have multiple identical backend Pods, the Service automatically load balances traffic among them.
